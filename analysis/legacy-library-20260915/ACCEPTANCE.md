## Observed path

After the earlier directory/file/writability checks in [REPORT.md](REPORT.md), the successful SqliteMountPoint initialization at `0x1297b88` allocates adapter objects (`0x1175e50` and `0x1176be8`), forms key-related data, and requires one derived string to have length `0x40` at `0x1297c90`. The actual constructor call at `0x1297ce8` passes the derived DB path in `x3` (`sp+0x60`) and a key candidate vector in `x6` (`sp+0xb0`) to `0x1179e60`, `SqliteDataBase` (source-path string VA `0x284c5d8`: `../../Source/Domain/MusicLibrary/Server/Rekordbox/DataBase/SQLite/SqliteDataBase.cpp`). The precise key derivation and material remain unresolved.

`SqliteDataBase` checks that the path is a usable string at `0x1179f14`, iterates candidate keys beginning at `0x1179f24` and `0x1179f30`, and opens the DB at `0x1179ffc` through `sqlite3_open_v2`, passing `w2=2` (`SQLITE_OPEN_READWRITE`) and `x3=0` (no VFS name). Nonzero open result branches away at `0x117a000`. It calls `sqlite3_key` at `0x117a02c`, passing the transformed key string pointer and its length; nonzero result branches away at `0x117a030`.

The first SQL acceptance probe is the literal `SELECT * FROM property` at VA `0x284c648` (file offset `0x244c648`). At `0x117a06c`, `sqlite3_prepare_v2` receives this query with length `-1`; its statement is finalized at `0x117a07c` **before any `sqlite3_step`**. A nonzero prepare result branches at `0x117a080` to an error path whose adjacent string at VA `0x284c660` says `sqlite3_prepare_v2() error (encrypt key is not correct)`. If every candidate fails, the constructor throws with the literal `cannnot decypt database` (VA `0x284c7b8`, call at `0x117a0d4`). Successful preparation therefore proves that the decrypted DB can compile a query against a `property` relation; it does not prove that the relation contains any particular row or library version.

After a key candidate works, `0x117a298` stores the SQLite handle, and `0x117a2b4` executes literal `PRAGMA main.journal_mode=delete` (VA `0x284c7d0`). Failure follows a database configuration error path. On success, `0x117a3a4` calls `0x1179720`, which executes `SELECT name from sqlite_master WHERE TYPE='table'` (VA `0x284c6a0`) at `0x11797a8`. The callback at `0x1177da0` collects the `name` column. For each table, `0x1179b3c` builds a dynamic `PRAGMA table_info(` + table name + `)` query (literal prefix VA `0x284c6d8`) and executes it at `0x1179ba4`; the resulting table/column metadata is copied to the database object's vector at `0x117a3b0`. The constructor returns at `0x117a430`. This is metadata enumeration, not evidence that a fixed table list is required at mount time.

The SqliteMountPoint path then stores the created DB object at `0x1297d0c` and returns success through the method's cleanup/return block (`0x1297b50` onward). There is no observed `property` row read or explicit version comparison in this bounded constructor trace.

## Interpretation and open gates

The filesystem gate can pass yet the native open can fail because the SQLite open, key application, `property` prepare, journal-mode configuration, or metadata query fails. The prepare error message frames failure as wrong encryption key, but SQL prepare can fail for other SQLite reasons (for example missing `property`), so it is not a reliable cause classifier. `SQLITE_OPEN_READWRITE` and the prior `W_OK` check mean a read-only source needs a writable overlay or copy for this native route; a DB that is merely present is insufficient.

The constructor does not show a `libraryVersion`, schema-version value, or supported OneLibrary release name. Those may be queried by later data-access operations; no claim of accepted playlist/cue/track schema follows from this trace. The earlier unknown absolute root prefix and unknown upstream `w5` selector remain unresolved. A host-side conversion proposal should be evaluated only after following later AZ table readers and their field expectations, then tested against a lawful, locally owned sample and ultimately the device. None of those tests was performed here.
