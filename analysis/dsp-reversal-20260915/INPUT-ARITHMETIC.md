# `0x1181a310` input arithmetic reconstruction

## Entry, modes, and buffer selection

IRQ8 calls `0x1181a310` at `0x1181aed8` with the normalized 0/1 link-derived buffer selector in `A4` (see `BUFFER-CONSUMERS.md`). The callee reads a signed halfword at `0x1183d40a` (`0x1181a310`–`0x1181a328`), tests it for 1 and 2 (`0x1181a32a`–`0x1181a338`), and skips the main conversion when neither test succeeds. Under the mode-1 predicate it constructs `A17=0x402e0d69` (`0x1181a358`, `0x1181a374`); under mode 2 it constructs `A17=0x3f61ceef` (`0x1181a38c`, `0x1181a394`). Interpreted as IEEE-754 binary32 these are approximately **2.7195684909820557** and **0.8820638060569763**. These are numeric mode gains; the halfword's product meaning and acoustic interpretation are not known.

The source base is `0x11800c00 + 704*selector` (`0x1181a336`–`0x1181a3c0`). The loop setup also forms 88-byte, 176-byte, and 352-byte offsets involving `B18`. `B18` starts at 1, increments after the software loop, and is compared with 3 before repeat. The combination at `0x1181a3ac`–`0x1181a3c0` subtracts a 352-byte offset after adding a `176*(B18+1)` offset. For the visible first pass (`B18=1`) it reduces to the selected buffer base; for the next (`B18=2`) it adds 176 bytes, exactly the McASP DMA lane stride. This supports **two 176-byte lanes per call**. It does not identify physical deck/channel names, and exact source-pointer phase inside the software pipeline remains to verify.

## Core arithmetic

The two visible integer lanes load 32-bit words at `0x1181a3d6` and `0x1181a3da`, perform signed arithmetic shifts by 8 at `0x1181a3e2` and `0x1181a3ec`, and apply `INTSP` at `0x1181a3e4` and `0x1181a3f4`. [TI's C67x instruction reference](https://www.ti.com/lit/ug/spru733a/spru733a.pdf) defines `SHR` as arithmetic and `INTSP` as signed integer-to-binary32 conversion. For an input word `x`, the uncontroversial intermediate is `f = float32(int32(x) arithmetic-right-shift 8)`.

The following bitfield sequence appears to scale `f` by an exact power of two without a multiply. It constructs mask `0x807fffff` in `A6` (`0x1181a350`, `0x1181a360`) to preserve sign and fraction while clearing the exponent; `EXTU ...,1,24` extracts the eight-bit binary32 exponent (`0x1181a404`, `0x1181a408`); `ADD` with `A7=-23` (`0x1181a34c`, `0x1181a36c`, `0x1181a410`, `0x1181a412`) reduces that exponent by 23; `EXTU ...,24,1` moves the adjusted eight bits back to binary32 exponent position (`0x1181a414`, `0x1181a428`); and `OR` combines the adjusted exponent with the preserved sign/fraction (`0x1181a420`, `0x1181a434`). The `CMPLTU` tests against 23 and predicated zero moves at `0x1181a418`–`0x1181a430` handle an exponent boundary. In the B-side packet `CMPLTU` writes `B1` and `OR` reads the prior exponent-field `B1` in parallel (`0x1181a418`/`0x1181a420`), so a straight line register interpreter would wrongly replace the exponent field with a one-bit predicate. The A-side packet has analogous write/read overlap near `0x1181a424`–`0x1181a434`. This is the reason compact execution packets matter.

For **every** possible signed 32-bit input word `x`, the arithmetic shift produces `s=int32(x)>>8` in `[-2^23,2^23-1]`; all such integers convert exactly to binary32 through `INTSP`. A nonzero converted value has exponent at least 127, so `CMPLTU(23,E)` is true and adjusted exponent `E-23` remains normal. Zero has exponent 0 and is selected to zero through the predicate moves. Under ordinary binary32 round-to-nearest assumptions, the recovered scalar core is **`float32((float32(s) * 2^-23) * gain[mode])`**, with gain bits `0x402e0d69` for mode 1 and `0x3f61ceef` for mode 2. Exponent rewriting performs the `2^-23` step exactly; only `MPYSP` can round the final multiplication. This is a static scalar reconstruction; output lane scheduling, DSP floating-control state, and native parity remain unverified. The input container is consistent with signed 24-bit PCM left-aligned in 32 bits; producer byte order and codec slot packing are not proven.

The independent [C consistency probe](check_input_core.c) compared the inferred exponent-bit rewrite with `float32(s) * 2^-23` for **all 16,777,216 signed 24-bit `s` values**, including zero and extrema, and compared both gain products. With nearest rounding and compiler fast-math disabled it found **zero bit mismatches** (`signed24_samples=16777216 modes=2 mismatches=0`). This validates the scalar algebra under the probe's IEEE assumptions; it does not execute DSP instructions or prove rendered-audio parity. [input_core_eval.py](input_core_eval.py) evaluates the candidate core for an arbitrary word and either mode.

## Stores and remaining gap

The two float values are written through advancing `B4`/`A5` by `STW` at `0x1181a446`/`0x1181a44a`. The routine constructs state bases `0x11839390` and `0x11839498` (`0x1181a3a0`–`0x1181a3b8`), and forms an 88-byte offset from `B18` (`0x1181a340`, `0x1181a344`, `0x1181a36e`). **The B-side pointer contradiction resolves at the packet boundary:** `MVK 22,B0` (`0x1181a3c2`) and `ADD B0,A3,B4` (`0x1181a3c4`) both carry `||` and execute in one packet after `SUB` at `0x1181a3c0`. The `ADD` reads the packet's pre-write `B0=0x11839390`; the `MVK` writes `22` for loop setup. Thus initial output pointers are `B4=0x11839390+88*B18` and `A5=0x11839498+88*B18`, with visible passes `B18=1,2`. The `SPLOOPD` has `ILC=21` (`0x1181a3c2`–`0x1181a3d4`), suggesting 22 scheduled iterations per pass; exact paired-load/store phase and total element coverage still require prologue/epilogue accounting. The numeric evaluator is restricted to the scalar core. It does not claim byte packing, paired-lane order, side effects, or native DSP parity.
